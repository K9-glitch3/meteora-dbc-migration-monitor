# Continuing the project

I am continuing DBC Migration Monitor independently of the Colosseum outcome.
The dated v0.2 and v0.3 public changes are post-submission work. I am not asking
for these commits to be counted as work completed during the judged period.

## Release gates I will use

1. Keep every supported claim tied to a reproducible capture or a labelled test.
2. Ask developers to try the workflow and record integration friction before
   expanding the API. The target is three accepted pilots and one real integration.
3. Count repeat usage only after a second dated external use, not my own testing.
4. Turn a reproducible external defect into a failing fixture, then a tested fix.
5. Obtain scoped outside review before describing any component as independently
   reviewed. A security review and a licensing review are separate activities.
6. Consider continuous hosted collection only after defining RPC budgets, retention,
   data-gap monitoring, delivery guarantees and an operator recovery procedure.

## Current limits

The public feed is manually refreshed from bounded samples. I have not sold a
continuous monitoring service or promised an uptime SLA. No paid infrastructure,
review engagement, wallet funding or transaction submission is authorized by this
release. A collector command must be deliberately run with bounded duration.

Three pilot invitations and one technical-review enquiry were sent on 16 October.
Acceptance, integration, repeat use and completed independent review are pending.
I will publish findings with permission rather than infer traction from outreach.

## What support would change

Funding could accelerate infrastructure and specialist review. It is not a
prerequisite for keeping the public toolkit reproducible, fixing defects, speaking
to developers or publishing honest progress. I will keep funded scope and current
self-funded work distinct.
